## What this project is

A local-first, multi-agent expense-claim system. Ingests receipt PDFs/images, extracts structured data with an on-device vision model, reconciles against locally stored travel requests and company policy, builds a claim, routes it through human review, records a tamper-evident audit trail, and exports XLSX — with zero receipt/personal data ever leaving the device.

## Tech stack (decided, don't re-litigate)

React + TypeScript + Vite + Tailwind CSS v4 · Dexie/IndexedDB (structured records) · OPFS (receipt binaries) · pdf.js + Canvas (document prep) · ONNX Runtime Web + WebGPU→WASM (on-device VLM) · Tesseract.js (OCR fallback) · Web Crypto SHA-256 (audit chain) · SheetJS (XLSX export) · XState (**Orchestrator only**, not every agent).

**Explicitly dropped:** Fuse.js — replaced with a plain weighted-score function for travel reconciliation (more explainable, one fewer dependency).

## Decisions that closed real plan gaps (do not silently reopen these)

1. **Duplicate detection** — dedup key is exact-file SHA-256 (reuse the audit hash) OR normalized vendor+date+amount+currency (normalize = lowercase, trim, strip punctuation). A hit on either → `DUPLICATE_SUSPECTED`, forced review, never auto-rejected. Owner: Sheet Populator (Phase 10).
2. **Currency handling** — Company Policy has a base currency + a static, manually-edited local conversion table (no live FX API — would violate zero-network). Currency missing from the table → `CURRENCY_UNSUPPORTED`, forced review. Ambiguous symbols (e.g. "$") are treated as missing, never guessed. Owner: Policy Engine (Phase 9).
3. **Model loading — bundle, don't fetch.** The quantized ONNX model ships as a static asset under `public/models/` in this repo, same-origin, not fetched from any external CDN. This is stronger than "cache after first online fetch" — there's no external network call to explain in the zero-egress writeup, and the offline claim holds from a cold start. Owner: Phase 5 (bundle it) + Phase 18 (verify with devtools network disabled).
4. **Tesseract fallback parser** — `ocrTextParser.ts` in the Validation module must emit a numeric confidence score alongside the extracted fields (fraction of required fields successfully parsed), not just the fields — otherwise it can't plug into the Phase 6 confidence gate. Owner: Phase 6.
5. **Travel reconciliation — employee ID is a mandatory hard filter**, not a weighted signal. (Original design weighted employee alongside date/destination — a real bug: a strong date+destination score could out-vote a wrong employee and link one person's receipt to someone else's trip. Fixed.) Only date proximity + destination are weighted, among that employee's own trips, for the HIGH/MEDIUM/LOW tier. Owner: Phase 8.
6. **File validation** — check actual file magic bytes (real PDF/JPEG/PNG signature), not just the extension, plus a 15MB hard size cap, before the file reaches pdf.js/Canvas. Owner: Phase 3.

### Post-P19 real-file demo (2026-09-24): real bug #15 found and fixed
Ran a genuine real-file demo at the user's request — not another synthetic single-line canvas receipt, but an actual saved PNG file with a realistic multi-line restaurant layout (stylized bold title, address, itemized lines, subtotal/tax/total, payment info). This is exactly why it's worth doing beyond the synthetic phase testing: it found a real bug synthetic tests never could, because every synthetic test receipt used a simple one-line vendor with no styling quirks.

**The bug**: `ocrTextParser.ts`'s vendor heuristic (first non-digit-starting line) had no defense against Tesseract completely failing to read a stylized title font — when that happened, it fell through to the next recognizable line (a phone number, "Tel: (555) 019-4472") and reported that as the vendor at a **false 100% confidence**, because the confidence score only checks field presence, not plausibility. A wrong-but-non-null value sailed straight through the exact gate meant to catch it.

**The fix**: added exclusion patterns for phone numbers and labeled metadata lines (tel/phone/fax/date/time/server/table/order/receipt/invoice), and restricted the vendor search to the first 5 lines so that if every early line is legitimately excluded, the heuristic returns `null` (honest, correctly drops confidence to 67%, triggers VLM fallback) instead of confidently mislabeling a line-item as the vendor. Verified against 3 cases: the real receipt now correctly returns null instead of the wrong phone number; a normal single-line receipt is unaffected; a receipt with the common real-world "vendor name, then phone number" layout now correctly picks the vendor, not the phone. Full real-file lifecycle (ingest→OCR low-confidence→VLM also honestly failed→human correction via the real UI→approve→export) verified live with the audit chain staying valid throughout. Committed: `f875b2d`.

**Lesson for future testing**: synthetic test fixtures, however varied, share the test-writer's own assumptions about what "normal" input looks like. A real (or at least realistically-varied, saved-to-disk) file is worth running through the pipeline at least once even after extensive synthetic coverage — it exercises OCR/rendering edge cases no hand-picked synthetic case will naturally hit.

### Real bug #16 (2026-09-24), found by the user running their own file: Extract button/thumbnail vanished after a page reload
The user uploaded a real receipt, the page reloaded before they extracted it (a plain refresh — not a crash), and the thumbnail and "Extract with on-device AI" button both disappeared entirely, even though `STORED RECEIPTS (1)` still correctly showed the record with its real file hash. Root cause: `UploadReceiptsPanel.tsx`'s `files` and `previews` state only ever lived in the component's memory, populated once at upload time via `handleFile` and never restored on mount — a reload wiped them while the underlying receipt record and actual file bytes (already safely in IndexedDB/OPFS per Phase 1) were completely untouched. Fixed in `refresh()`: for any stored receipt not yet seen this session, read its file back from OPFS via the already-existing `readReceiptFile()` and re-populate both `files` and `previews`, restoring full functionality without requiring a re-upload of something already saved. A `useRef` set tracks which receipts have already been restored so this doesn't repeat on every `refresh()` call, and `handleFile` marks a freshly-uploaded receipt as already-restored before calling `refresh()` so the restoration pass doesn't redundantly re-read and re-process a file already in hand. Also caught and fixed a subtler issue while writing this: an earlier draft called `runProcessing()` as a side effect inside a `setPreviews()` updater function, which is unsafe under React StrictMode (updater functions can run more than once and shouldn't have side effects) — restructured to call it directly, guarded by the restoration ref instead. Verified live by reproducing the exact scenario: upload → reload before extracting → thumbnail and Extract button both correctly reappeared → clicked Extract on the OPFS-restored file → extracted correctly, same as a fresh upload. Zero console errors. Committed: `e1915b4`.

### Gap-closing pass (2026-09-27): 4 real fixes, 1 real bug found in the process, 2 deliberate non-fixes
Prompted by a fresh gap analysis against the official problem statement's evaluation criteria. Four targeted, verified fixes:

1. **Real bug #17 found live while testing something else**: a second vendor-misdetection case, distinct from bug #15's phone-number one. When a receipt's title is in a script/cursive font Tesseract reads as nothing at all, the vendor search can fall through to a genuine line item ("Grilled Salmon 24.00") — which matches neither existing exclusion pattern, so it's accepted as the vendor at a false 100% confidence. Fixed with a new `LINE_ITEM_LIKE_PATTERN` exclusion (`ocrTextParser.ts`): a real vendor name never ends in a receipt-formatted price; a line item does. Verified live: the failing case now correctly returns `vendor: null` at 67% confidence (correctly triggering the VLM fallback) instead of confidently mislabeling a line item; the normal case ("Test Cafe") re-verified unaffected.

2. **Tesseract crash recovery completed, not just documented as partial.** The existing self-heal only covered worker *initialization* failure. A crash during `recognize()` itself left the same corrupted worker cached, requiring a page reload — the previously-documented "partially resolved" limitation. Fixed by mirroring the extraction Worker's own proven crash-recovery pattern: terminate + drop the cached reference on ANY failure, not just init, so the next call gets a genuinely fresh worker (`ocrTextParser.ts`).

3. **Travel-request tie detection added**, mirroring the Category Classifier's existing tie-handling pattern (the known, documented low-priority gap from Phase 8). Two approved trips for the same employee scoring identically now correctly return `REVIEW` naming both candidates instead of silently picking one. Verified live against 5 cases: a genuine tie (correctly flagged, both destinations named), a normal single match (unaffected), no approved trips (unaffected), a full MATCHED case (unaffected), and a genuine non-tie between two candidates (correctly picks the actually-better one, not a false tie).

### Full codebase audit (2026-09-27): every source file reviewed, 4 more real gaps found and fixed

### New feature (2026-09-27): a real, honest fake-bill signal — line-item vs total consistency
User asked directly whether there's any method to identify fake bills. ### Investigated and reverted (2026-09-27): swapping to a smaller VLM (smolvlm-256m-instruct) to cut fallback latency
User flagged the AI-fallback path's ~5 minute cost as top priority. Before changing anything, measured where the time actually goes rather than guessing:

- **Model loading: 9.3s.** Not the bottleneck — pre-warming would have saved under 3% of the total wait. This ruled out the fix I was about to build.
- **A single inference call, on that already-warm model, on a tiny 400×200px image, took 386s** — worse than the documented 213-241s baseline, consistent with the already-known thermal-throttling-over-a-long-session finding (this session had already run many back-to-back VLM calls by this point).
- **The model's own output was short (~60-80 tokens)** and stopped naturally, well under even a 150-token cap — so trimming the token budget further had nothing left to trim.

Conclusion: the cost is the model's own per-call compute (running a 500M-parameter vision-language model fully in-browser), not load time or output length. The only real lever left was a smaller model. With the user's explicit go-ahead, downloaded `HuggingFaceTB/SmolVLM-256M-Instruct`'s int8 ONNX files directly from Hugging Face (verified byte-for-byte against the reported Content-Length for all three: decoder 137MB, vision encoder 94MB, embed tokens 28MB — a real ~2.5x reduction in the decoder specifically, the component that runs once per generated token). Total bundle dropped from 493MB to ~260MB.

**Result: a real but unreliable speedup, and a serious accuracy failure.** Two live tests against the exact same images used to establish the 500M baseline:
1. A script-font vendor test: 171.7s (vs 386s, ~2.2x faster) — but the model **invented an entirely different JSON schema** (`menu`, `menu_price`, `menu_items_total`) instead of the one the prompt asked for. Every requested field came back null.
2. A simple, clean typed receipt — the easy case: 316.5s (barely faster than the 500M baseline, within normal variance) — and the model **degenerated into a malformed, non-JSON, repeating hallucination loop** ("Test Café" repeated until it hit the 200-token cap), never producing valid JSON at all.

Two out of two real tests: zero usable extracted data. **Reverted immediately** — `MODEL_ID` back to `smolvlm-500m-instruct`, the downloaded 256M model files deleted (`public/models/` is gitignored regardless, so this was never a commit-hygiene issue, just wasted local disk), and the UI/comment text that had been updated for the smaller model's numbers reverted to match. A faster pipeline that can't reliably extract data is strictly worse than a slower one that works — this wasn't a case where "good enough, ship it" applied.

**What this establishes for whoever picks this up next**: the 500M model's speed is a genuine, hardware-bound floor for this exact architecture, not a configuration oversight — pre-warming, token-budget trims, and a smaller same-family model were all tried, measured, and ruled out in this one session. The one lever not yet tried: a smaller model with a deliberately simpler extraction task (e.g. asking it for only the total amount as a single number, not a full JSON object with vendor/date/currency/lineItems) — the 256M model's failures both involved schema/structure adherence, not obviously the core visual reading task itself, so a much simpler ask might fare better. Not attempted here — a genuinely different experiment, not a quick follow-up. `tsc -b` and `vite build` both clean after the revert.

### New feature (2026-09-24): policy-PDF import, "suggest, never auto-save" (Version A)
The user asked whether Company Policies could be filled in by uploading the actual policy PDF instead of typing every category/limit by hand, and immediately self-imposed the same constraint the rest of the project already follows: no API calls, on-device only. Reused the existing extraction Worker infrastructure end to end rather than building a second one — added a `task: 'receipt' | 'policy'` discriminator to the Worker's request/response contract, factored the shared model-invocation path out of `runExtraction` into `runVlmPrompt()` (`extractionWorker.ts`), and added a parallel `extractPolicyPage()` in `extractReceipt.ts` that shares the exact same singleton worker, serialized send queue, crash recovery, and 11-minute client-side timeout as receipt extraction — so a policy-PDF read happening around the same time as a receipt extraction correctly queues instead of contending, with no new robustness code needed. `renderPdfPages()` (`processDocument.ts`) renders up to `MAX_POLICY_PDF_PAGES` (3) pages of a policy document — capped, unlike receipts' fixed single page, since a real policy PDF can run several pages but each page costs a real multi-minute on-device read. The new orchestrating agent, `src/agents/policy-import/extractPolicyFromPdf.ts`, validates the upload is a genuine PDF by magic bytes (reusing `detectFileKind`), renders the pages, calls `extractPolicyPage` on each with a progress callback, and dedupes candidates by category (keeping the last occurrence, on the theory that a later mention is more likely the specific rules section than an earlier summary).

**Why "ask before saving" and not auto-save**: this is the one place in the app that deliberately breaks from receipt extraction's pattern of writing a nullable/best-effort result straight into a record for later human review. A wrong receipt field gets caught by the review queue before a claim is approved; a wrong **policy limit** would silently become the rule every future receipt is checked against, with nothing downstream to catch it. So `PoliciesPanel.tsx` shows every candidate rule as an individually-confirmable suggestion (its own "Add" and "Dismiss" buttons) in a completely separate `suggestions` state — nothing touches `db.policies` until a human clicks Add on that specific row. Suggestions are intentionally ephemeral (lost on reload), matching the same "isn't real until it's actually the persisted rule" boundary already used for `UploadReceiptsPanel`'s in-progress extraction summaries.

**Real bug found and fixed during live testing**: on a real synthetic multi-line policy PDF (Meals/Travel/Lodging/Communication with distinct limits), the VLM read every value correctly but returned them as JSON strings (`{"limitAmount": "45"}`) rather than numbers — `normalizePolicyCandidates`'s original strict `typeof === 'number'` check silently dropped all 4 correct candidates, showing "No spending limits found" even though the model had gotten everything right. Fixed with `coerceLimitAmount()` in `extractionWorker.ts` (accepts a number as-is, coerces a non-empty numeric string via `Number()`, otherwise `NaN` so the existing `Number.isFinite` filter still drops genuine junk). **Note for later**: `normalizeExtracted()` (receipt path, same file) has the identical strict `typeof === 'number'` pattern for `amount` and line-item amounts, which could have the same latent failure mode — not changed here since receipts have tested correctly across many live runs this session and changing untested-as-broken code without a reproduced failure would be unjustified scope creep, but worth remembering if a future receipt test ever shows a correct-looking VLM read reported as a dropped/null amount.

**Verified live end-to-end**, using a hand-built minimal PDF (no external PDF library available in this project, so the file itself was constructed directly in raw PDF syntax) with 4 distinct category/limit lines: uploaded through the real file input (the embedded test browser pane can't drive a native OS file picker, so the `<input type=file>`'s `.files`/`change` event was set via `DataTransfer` in-page JS instead — a testing-tool workaround, not a change to how the feature itself works), watched the real "Reading page 1 of 1…" progress state, got all 4 correct candidates back once the coercion fix landed, clicked Add on one (Meals) and Dismiss on another (Travel), confirmed the Category Spending Limits list updated live with only the added one, reloaded the page and confirmed the added rule persisted while the two untouched/never-decided suggestions (Lodging, Communication) correctly did not appear anywhere — nothing was silently saved for them. ### Bug pattern worth remembering: requestAnimationFrame + backgrounded tabs
Any future code that renders to a canvas or otherwise depends on `requestAnimationFrame` (not just pdf.js) will stall indefinitely if the browser tab isn't in the foreground — Chromium suspends rAF callbacks entirely for hidden tabs, and this doesn't throw or reject, it just never fires. If something HANGS with zero console output, check `document.hidden` and look for rAF-based scheduling before assuming the code is broken. Prefer non-rAF scheduling (`Promise.resolve().then()`, `setTimeout`) or a library's own non-interactive/background render mode where one exists, plus a timeout as a safety net.

### Testing note for whoever picks this up
The browser automation's programmatic `form_input` on a React-controlled text input does **not** reliably trigger React's `onChange` (it sets the DOM value without the event React's synthetic system listens for) — this produced a false "nothing happened" reading during P2 testing. Verified via direct IndexedDB inspection that the underlying action actually succeeded; confirmed the pattern by retrying with real click+type keystrokes, which work correctly every time. **When verifying a form in the browser, prefer simulated keystrokes (click the field, then type) over programmatic value-setting for anything wired to React state.** Date/select inputs via `form_input` were fine in this case — the issue only showed up on plain text inputs.

A second, related gotcha surfaced during the full E2E pass: reading the page **immediately** after a click can outrun the async Dexie query inside the component's `useEffect`/refresh — looked like a real data-loss bug (a policy rule "disappeared" after reload) until a direct IndexedDB query proved the record was there all along, and a re-check a moment later showed it correctly in the UI too. **When verifying persistence, add a short wait (or re-check) after a reload before concluding data is missing** — don't take the very first read as final.

### Original scoping notes (kept for context)

### PostgreSQL attached (2026-10-05) — in-browser, mirrored, still zero-network

**Why:** the project was asked to be backed by PostgreSQL. A server database would break the on-device, zero-network requirement, so this uses PGlite — the real PostgreSQL engine (v18) compiled to WebAssembly — running inside the browser and persisted to this device's own storage (`idb://claimsense-pg`).

**How:** `modules/storage/pg.ts` defines a real SQL schema (6 tables, primary keys, foreign keys incl. a self-reference on `claims.duplicate_of_claim_id`, CHECK constraints, indexes, NUMERIC/TIMESTAMPTZ/JSONB types). Dexie remains what the app reads and writes; Dexie table hooks mirror every create/update/delete to Postgres *after the transaction commits*, serialised through one queue, with failures logged and never thrown — so the mirror cannot break the app. On startup it also copies across anything already in Dexie. A new "Database (SQL)" tab runs read-only SQL (SELECT/WITH/EXPLAIN/SHOW only; writes are rejected) with preset queries (JOIN, aggregate, audit chain, table counts).

**Verified live:** 3 receipts through the real pipeline → 3 claims, 3 receipts, 7 audit rows in Postgres; approval propagated; JOIN across claims/receipts, GROUP BY, and audit `previous_hash → current_hash` chain all return correct rows; rows inserted directly into IndexedDB (bypassing the hooks) were picked up by the startup backfill; `DELETE` from the console is rejected; data survives a reload; production build succeeds with the Postgres wasm/data bundled and precached for offline use.

**Honest scope:** Postgres is a mirror, not the system of record — Dexie still serves the app's reads. Replacing Dexie outright was the riskier alternative and was deliberately not done the day before a demo.

### PostgreSQL is now the system of record (`9a83f90`)

## Session 2026-11-05 — pre-submission audit against the problem statement

### Real problems found and fixed
1. **The on-device AI loaded its engine from a CDN.** Since `@huggingface/transformers` v4, ONNX Runtime's `wasmPaths` default to `https://cdn.jsdelivr.net/npm/onnxruntime-web@…/dist/` unless the app sets them. The worker's `fetch` guard blocked the `.wasm`, but the engine's `.mjs` loader is fetched with `import()`, which that guard can't see. Net effect: the AI fallback was either reaching a CDN for code or failing. Found only because of fix 2 below. `vlmRuntime.ts` now points `wasmPaths` at the copies Vite bundles from `node_modules`, served same-origin. Verified live: the fallback ran on WebGPU and returned a result, and the only host contacted was `localhost`.
2. **Zero egress is now enforced by the browser, not just by our own code.** The production build carries a Content-Security-Policy (`connect-src 'self'`, `script-src 'self' 'wasm-unsafe-eval' blob:`), also sent as a header by `vite preview` so it covers every worker. A deliberate `fetch('https://example.com/collect')` from the page is refused. Dev server excluded (hot reload needs inline scripts and a WebSocket).
3. **Correcting a claim didn't re-check the policy.** A misread $50 meal corrected to $500 still showed (and exported) PASS against a $75 limit. `editClaim` now re-runs the Policy Engine when amount, currency or category change, moves a draft to review if it no longer passes, and logs `POLICY_REEVALUATED`. It also refuses to edit an approved claim (the UI already hid the fields; the agent didn't enforce it).
4. **"Approve & submit" discarded unsaved corrections**, approving the old values. It now saves first, and stops if the save fails. The receipt **date** is now editable too (it was display-only, so a date OCR missed could never be filled in).
5. **One receipt at a time.** The brief says "a folder of receipts"; the picker took one file and each receipt needed its own Extract click. Now: multi-file upload (each rejected file named, the rest continue) and "Extract all", which runs them one after another through the Orchestrator. After a reload, receipts that already have a claim show "Claim already created" instead of an Extract button that would have built a duplicate claim.

Smaller: OCR missed the currency when the code runs into the price (`INR12.00`), found by the new tests; the PDF.js worker and ONNX loader (`.mjs`) were never in the offline precache; amounts now show two decimals; lint no longer scans the vendored Tesseract files.

### Third pass the same day: edge-case testing
Every form was driven with bad input in the browser, plus the SQL console with attack queries, receipts in other date formats, and the full pipeline with the server stopped.
