## What this project is

A local-first, multi-agent expense-claim system. Ingests receipt PDFs/images, extracts structured data with an on-device vision model, reconciles against locally stored travel requests and company policy, builds a claim, routes it through human review, records a tamper-evident audit trail, and exports XLSX — with zero receipt/personal data ever leaving the device.

## Tech stack (decided, don't re-litigate)

React + TypeScript + Vite + Tailwind CSS v4 · Dexie/IndexedDB (structured records) · OPFS (receipt binaries) · pdf.js + Canvas (document prep) · ONNX Runtime Web + WebGPU→WASM (on-device VLM) · Tesseract.js (OCR fallback) · Web Crypto SHA-256 (audit chain) · SheetJS (XLSX export) · XState (**Orchestrator only**, not every agent).

**Explicitly dropped:** Fuse.js — replaced with a plain weighted-score function for travel reconciliation (more explainable, one fewer dependency).

## Decisions that closed real plan gaps (do not silently reopen these)

1. **Duplicate detection** — dedup key is exact-file SHA-256 (reuse the audit hash) OR normalized vendor+date+amount+currency (normalize = lowercase, trim, strip punctuation). A hit on either → `DUPLICATE_SUSPECTED`, forced review, never auto-rejected. Owner: Sheet Populator (Phase 10).
2. **Currency handling** — Company Policy has a base currency + a static, manually-edited local conversion table (no live FX API — would violate zero-network). Currency missing from the table → `CURRENCY_UNSUPPORTED`, forced review. Ambiguous symbols (e.g. "$") are treated as missing, never guessed. Owner: Policy Engine (Phase 9).
3. **Model loading — bundle, don't fetch.** The quantized ONNX model ships as a static asset under `public/models/` in this repo, same-origin, not fetched from any external CDN. This is stronger than "cache after first online fetch" — there's no external network call to explain in the zero-egress writeup, and the offline claim holds from a cold start. Owner: Phase 5 (bundle it) + Phase 18 (verify with devtools network disabled).
4. **Tesseract fallback parser** — `ocrTextParser.ts` in the Validation module must emit a numeric confidence score alongside the extracted fields (fraction of required fields successfully parsed), not just the fields — otherwise it can't plug into the Phase 6 confidence gate. Owner: Phase 6.
5. **Travel reconciliation — employee ID is a mandatory hard filter**, not a weighted signal. (Original design weighted employee alongside date/destination — a real bug: a strong date+destination score could out-vote a wrong employee and link one person's receipt to someone else's trip. Fixed.) Only date proximity + destination are weighted, among that employee's own trips, for the HIGH/MEDIUM/LOW tier. Owner: Phase 8.
6. **File validation** — check actual file magic bytes (real PDF/JPEG/PNG signature), not just the extension, plus a 15MB hard size cap, before the file reaches pdf.js/Canvas. Owner: Phase 3.

### Architecture change (2026-09-23): OCR now runs before the VLM, not after
Originally the pipeline always ran the slow on-device VLM first and used OCR (Tesseract) only as a fallback when the VLM was low-confidence. Measured data across every real test this session showed that was backwards: OCR reads a clean typed receipt in well under a second and correctly got the field (amount) the VLM kept failing, every time, while the VLM alone took 3-6+ minutes. Flipped `validateExtraction()` to try OCR first and only invoke the VLM (now the fallback) when OCR itself is incomplete/low-confidence. Verified live: two clean receipts dropped from ~5-6 minutes to ~22s (cold Tesseract start) and ~12s (warm), same accuracy; a deliberately unreadable image correctly still fell through to the VLM, proving the fallback path still works. Committed `753267a`. **If a future phase changes receipt scope to include harder inputs (handwriting, heavy blur/glare), expect the VLM-fallback path to trigger more often and re-measure typical latency — the 22s/12s numbers assume clean typed receipts, the project's stated demo scope.**

### New finding (2026-09-23): VLM latency/confidence degrade during long sessions
Two Phase 10 test runs took ~580-600s with 0% AI confidence, vs. 213-241s / 67% confidence earlier the same day, with no code change in between — consistent with thermal throttling after sustained heavy compute (many VLM runs back-to-back). Not yet root-caused. If replicating this testing pattern, expect real degradation over a long session, not a fixed number — and the 10-minute extraction timeout above exists specifically because of this.

### Testing note: don't edit Worker source files mid-extraction
Editing `extractionWorker.ts` while a live extraction was in flight caused Vite to reload the page, silently orphaning that extraction (all progress lost, no error surfaced). Not a production bug — a real user wouldn't hot-edit source code mid-use — but a real trap for whoever tests this next: finish or explicitly abandon an in-flight extraction test before editing any file the dev server would hot-reload.

### Bug pattern worth remembering: requestAnimationFrame + backgrounded tabs
Any future code that renders to a canvas or otherwise depends on `requestAnimationFrame` (not just pdf.js) will stall indefinitely if the browser tab isn't in the foreground — Chromium suspends rAF callbacks entirely for hidden tabs, and this doesn't throw or reject, it just never fires. If something HANGS with zero console output, check `document.hidden` and look for rAF-based scheduling before assuming the code is broken. Prefer non-rAF scheduling (`Promise.resolve().then()`, `setTimeout`) or a library's own non-interactive/background render mode where one exists, plus a timeout as a safety net.

### Testing note for whoever picks this up
The browser automation's programmatic `form_input` on a React-controlled text input does **not** reliably trigger React's `onChange` (it sets the DOM value without the event React's synthetic system listens for) — this produced a false "nothing happened" reading during P2 testing. Verified via direct IndexedDB inspection that the underlying action actually succeeded; confirmed the pattern by retrying with real click+type keystrokes, which work correctly every time. **When verifying a form in the browser, prefer simulated keystrokes (click the field, then type) over programmatic value-setting for anything wired to React state.** Date/select inputs via `form_input` were fine in this case — the issue only showed up on plain text inputs.

A second, related gotcha surfaced during the full E2E pass: reading the page **immediately** after a click can outrun the async Dexie query inside the component's `useEffect`/refresh — looked like a real data-loss bug (a policy rule "disappeared" after reload) until a direct IndexedDB query proved the record was there all along, and a re-check a moment later showed it correctly in the UI too. **When verifying persistence, add a short wait (or re-check) after a reload before concluding data is missing** — don't take the very first read as final.

## Phase 5 — measured results (the old "5-30s" estimate was wrong, now replaced with real data)

**The on-device VLM genuinely works.** SmolVLM-500M-Instruct (int8 ONNX, ~511MB), loaded entirely same-origin from `public/models/` — confirmed via live network log, zero requests left localhost. Tested against 3 real (synthetic but genuinely printed-text) receipts:

- **Vendor and date extracted correctly on 3/3.** Real content understanding, not just infrastructure working.
- **Amount/total extraction failed on 3/3.** A real, reproducible weakness, not noise — worth a future prompt-engineering pass, but not urgent: the confidence gate already correctly drops to 67% (2 of 3 required fields) and routes these to human review exactly as the plan designs it to. This is the safety net working, not a silent wrong answer reaching a claim.
- **Latency measured at 213–241 seconds/receipt** on real hardware (Intel Gen-12 integrated GPU, confirmed genuine WebGPU adapter via `adapter.info`, not a software fallback) — roughly 10x the plan's original 5-30s guess, which was an untested estimate. Cutting `max_new_tokens` 256→128 only reduced latency ~10%, not the ~50% a token-count-dominated model would predict — per-call/session overhead dominates more than expected. **This number is now a real decision point, not a guess**: at 3-4 minutes/receipt, a demo needs to budget for that explicitly (pre-load the model before the live part, don't extract on stage from cold), and if that's unacceptable, the next lever to pull is a smaller model (e.g. SmolVLM-256M) traded against further accuracy loss, not more prompt tuning.

Two real bugs found and fixed during this testing, not just the happy path:
1. **Extraction was running on the main thread** — the phase's own goal explicitly said "in a Web Worker" and this was missed initially, caught only by rereading the plan mid-test. Fixed: `src/workers/extractionWorker.ts`, verified by switching tabs mid-extraction and confirming the UI stayed responsive.
2. **Dashboard tabs were unmounting/remounting panels on switch**, silently losing in-flight extraction state — a multi-minute call with nowhere for its result to land if you looked away. Fixed: `src/App.tsx` now keeps all panels mounted, toggling visibility with the `hidden` attribute instead of conditional rendering. Verified by re-running the tab-switch test after the fix.

## PWA / Service Worker (Phase 17b) — optional, not required, don't over-prioritize

**"Zero data egress" has two different meanings.** Right now (and even after P5-P19 are done) the app requires a running server to load (`npm run dev`, or *some* HTTP server for `dist/`) — that's normal for a web app. "Zero network" as actually required means *receipt/personal data never leaves the device*, which doesn't depend on a Service Worker at all. The stronger claim — *the app itself opens with zero network* — is what a Service Worker would add.

**Checked this against the official problem statement's evaluation criteria (the ground truth), not just our own tech-stack table, before deciding whether to build it: it is NOT required for grading.** Evaluation covers extraction/policy accuracy, orchestration robustness, on-device operation for sensitive data, review-flow usability, and code quality — none of that needs the app shell to load offline. It IS a legitimate architectural choice already on record in the R&A doc (which explicitly rejected Electron/Tauri in favor of PWA for the "one-tab browser-local" reason), so it's not a fabricated task — just correctly optional.

**Current status: Phase 17b, marked OPTIONAL/stretch on the tracker, scheduled last, not blocking anything.** Build it only if P0–P19 (the graded pipeline) are solid first. Do not let it eat time that belongs to Phase 5 onward.
