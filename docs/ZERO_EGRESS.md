# Zero Data Egress — How It's Guaranteed

ClaimSense processes every receipt entirely on the machine it's running on. No receipt image, extracted field, policy rule, or claim record is ever transmitted anywhere. This is enforced in independent ways, not just assumed:

1. **The AI model runs locally, not against an API.** The vision-language model and OCR engine are bundled with the app itself and loaded from the same origin — there is no call to any cloud inference endpoint (OpenAI, Google, AWS, etc.) at any point. Extraction runs inside a dedicated Web Worker via ONNX Runtime Web (WebGPU, falling back to WASM).

2. **The Worker's own network access is structurally blocked, not just unused.** Standard browser network-monitoring tools don't observe requests made from inside a Worker's own context — a real gap found during testing. To close it, the Worker's `fetch` function is intercepted at the source (`src/workers/extractionWorker.ts`): any request that isn't same-origin (i.e. not the app's own bundled files) is rejected outright and logged as an error, rather than allowed to silently succeed. This turns "we don't call out" from a design intention into an enforced constraint.

3. **The browser itself refuses any request to another host.** The production build ships a Content-Security-Policy (`vite.config.ts`) whose `connect-src 'self'` and `script-src 'self'` make the browser block every fetch, XHR, WebSocket and script load to any other host, from any library, before it leaves the page. `vite preview` also sends it as an HTTP header, which covers the OCR, PDF and database workers too. This is not just theory: in the pre-submission audit (2026-11-05) it caught a real leak. Since `@huggingface/transformers` v4, the AI runtime loads its engine from `cdn.jsdelivr.net` unless the app says otherwise, and the engine's loader uses `import()`, which the worker's `fetch` guard in point 2 can't see. The engine is now bundled with the app and loaded same-origin (`src/modules/ai/vlmRuntime.ts`), and the policy blocks any future regression of this kind. A deliberate `fetch('https://example.com/…')` from the page is refused with a CSP error.

4. **All storage is local, and there is no server.** Receipt records, extracted data, travel requests, policies, claims, and the audit log live in a PostgreSQL database that runs *inside the browser* (PGlite — the real Postgres engine compiled to WebAssembly, `src/modules/storage/pg.ts`), persisted to that device's own IndexedDB; receipt files themselves live in OPFS (Origin Private File System). "PostgreSQL" here does not mean a database server: nothing listens on a port, and nothing is sent anywhere. There is no backend to sync to, because none exists. Currency conversion uses a static, locally-entered rate table rather than a live FX API, for the same reason.

5. **The app itself can run with no network at all.** A service worker precaches the app shell, the OCR engine and its English language data, the database engine, and the AI runtime, so after the first visit ClaimSense opens and processes receipts with the network fully off (verified by stopping the server and cold-reloading). The AI model's weights are the one exception: the 365 MB decoder is larger than the browser's cache will store as a single file, so the on-device AI fallback needs the app's own server reachable once per session to load it. When it can't, the receipt goes to human review rather than failing. Clean receipts read by OCR are unaffected.

The only point at which data can leave the device is the final export step, where the approved claim is written to a local `.xlsx` file (generated entirely client-side via SheetJS, `src/agents/export/exportClaims.ts`). What happens to that file afterward — whether it's emailed, printed, or left on disk — is a decision made by the person using the app, not an action the software itself performs.

**Verified (2026-11-05, production build)**: a full run of four receipts (upload → OCR → classify → reconcile → policy → claim → review → approve), plus the on-device AI fallback, contacted only `localhost`. The browser's own resource log lists no other host, and no CSP violation was reported other than the deliberate test request.
